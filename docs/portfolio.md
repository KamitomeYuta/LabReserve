# เปลี่ยน reference project เป็นหลักฐานความสามารถของคุณ

โค้ดตั้งต้นนี้ AI ช่วยสร้าง ผู้เรียนควรระบุบทบาทตามจริง การอ่านโค้ดอย่างเดียวไม่เท่ากับการออกแบบและพัฒนาทั้งระบบด้วยตัวเอง สิ่งที่คุณเพิ่ม ทดลอง และอธิบายได้จะเป็นหลักฐานของคุณ

## งานที่ควรทำด้วยตัวเองหลังเรียน

1. เพิ่มกติกาจองล่วงหน้าได้ไม่เกิน 30 วัน เขียน boundary tests ก่อนเปลี่ยน rules
2. เพิ่มตัวกรองเฉพาะอุปกรณ์เปิดรับจอง โดยแก้ schema/query/UI และ tests
3. ใช้ EXPLAIN ANALYZE กับ query รายการจองบนข้อมูลจำลอง แล้วเขียนเหตุผลก่อนเพิ่ม index
4. จำลอง database unavailable ใน environment ทดลอง ตรวจ request ID และเขียน incident report

แต่ละงานควรมี issue ที่บอกปัญหา, commit ที่อธิบายการเปลี่ยน, test ที่เคย fail, ผลหลังแก้ และข้อจำกัด อย่าเติมตัวเลข latency หรือจำนวนผู้ใช้ที่ไม่เคยวัด

## ตัวอย่างคำอธิบายที่ตรงไปตรงมา

> ศึกษาและต่อยอดระบบจองอุปกรณ์จาก reference project ที่พัฒนาร่วมกับ AI เพิ่มกติกา [สิ่งที่ทำเอง] พร้อม [test ที่เขียนเอง] ทดลอง [สถานการณ์] และบันทึกผล [ลิงก์หลักฐาน]

## หัวข้อที่ควรตอบได้โดยไม่เปิดเฉลย

- TypeScript ต่างจาก runtime validation อย่างไร?
- ทำไม SELECT ว่าว่างก่อน INSERT ยังเกิดจองซ้ำ?
- Row lock กับ exclusion constraint ป้องกันคนละปัญหาอย่างไร?
- ทำไมต้อง authorize ที่ server แม้หน้าจอซ่อนปุ่มแล้ว?
- Cookie HttpOnly และ CSRF token ทำหน้าที่ต่างกันอย่างไร?
- ถ้าบันทึก event ไม่สำเร็จ รายการจองจะเป็นอย่างไร?
- เวลาไทย 10:00 ที่เก็บเป็น UTC แสดงกลับอย่างไร?
- การ deploy ผ่านกับการดูแล production ต่างกันตรงไหน?

## คลิป demo 3–5 นาที

อธิบายปัญหาผู้ใช้ → จองหนึ่งรายการ → แสดง conflict → เปิด test ที่ยืนยัน → อธิบายข้อแลกเปลี่ยนหนึ่งเรื่อง → บอกสิ่งที่คุณเพิ่มเองและสิ่งที่ยังไม่ได้ทำ
