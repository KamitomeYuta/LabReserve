# 08 — Race condition: ทดลองให้เห็นก่อนแก้

**ก่อนเริ่ม:** เข้าใจ transaction และทำ integration tests ได้

**เป้าหมาย:** พิสูจน์ว่า check-then-insert ไม่ atomic และอธิบายบทบาท lock กับ constraint

## ทำความเข้าใจ

Lab นี้แยกจากแอปจริงและใช้ฐานชื่อท้าย _race_test เท่านั้น สคริปต์บังคับให้ client สองตัวอ่าน slot ว่างก่อนทั้งคู่ insert จึงเห็น race โดยไม่อาศัย timing โชคดี จากนั้นใช้ UNIQUE กับ slot คงที่เพื่อให้หนึ่ง insert ถูกปฏิเสธ

แอปจริงจองเป็นช่วงเวลา จึงใช้ EXCLUDE + tstzrange แทน UNIQUE ธรรมดา [start,end) ยอมให้ช่วงติดกันได้ เมื่อ PostgreSQL ส่ง 23P01 API แปลงเป็น 409

Lock equipment ใช้เรียงการจองกับการปิดรับจอง ส่วน constraint ป้องกันช่วงซ้อนแม้มี writer ที่ไม่ใช้ service เดิม ต้องเข้าใจทั้งสอง ไม่ควรแก้ conflict ด้วย retry แบบไม่คิด เพราะเป็นธุรกรรมที่ผู้ใช้ต้องเลือกเวลาใหม่

## ลงมือทดลอง

คำสั่งจากรากโปรเจกต์ (โฟลเดอร์ที่มี package.json):

```bash
docker compose exec db createdb -U labreserve labreserve_race_test
DATABASE_URL=postgres://labreserve:labreserve_local@127.0.0.1:55432/labreserve_race_test npm run lesson:race
```

**ผลที่ควรเห็น:** Naive check-then-insert rows: 2; With unique constraint: fulfilled, rejected; Protected rows: 1

**ถ้าติดปัญหา:** createdb ทำครั้งแรกเท่านั้น; ถ้าเลือกพอร์ตอื่นแก้ URL ให้ตรงกัน; สคริปต์ล้างเฉพาะ teaching_race ในฐาน lab ห้ามเปลี่ยน guard ให้รับฐานจริง

## แบบฝึกหัด

อ่าน test overlapping concurrent booking และ adjacent bookings แล้ววาดลำดับคำขอ A/B ที่ทำให้ check-then-insert ผิด
