# ปิดรับจองแล้วคำอธิบายอุปกรณ์หาย

ระหว่างทดลองเดโม เจ้าของโปรเจกต์รายงานว่าเมื่อกด **ปิดรับจอง** คำอธิบายของอุปกรณ์หายไป สิ่งที่คาดหวังคือสถานะเปลี่ยนเป็นปิดรับจอง โดยชื่อและคำอธิบายยังคงเดิม เมื่อตรวจฐานข้อมูลพบว่า CAM-001 และ OSC-001 มีคำอธิบายเป็นข้อความว่างจริง

## ตามหนึ่งคำขอจากปุ่มถึงฐานข้อมูล

เมื่อกดปุ่ม หน้าแอดมินส่ง `PATCH /api/v1/equipment/:id` พร้อม `{"active":false}` ตัวตรวจข้อมูล Zod สำหรับการแก้ไขสร้างมาจากกติกาของการเพิ่มอุปกรณ์ ซึ่งกำหนดค่าเริ่มต้นของคำอธิบายเป็นข้อความว่าง หลังตรวจข้อมูล API จึงได้ `{"active":false,"description":""}` แม้ผู้ใช้จะไม่ได้แก้ช่องนี้

ตอนบันทึก SQL ใช้ `COALESCE($4, description)` เพื่อเก็บค่าเดิมเมื่อไม่ได้ส่งคำอธิบาย แต่ข้อความว่างเป็นค่าที่บันทึกได้ ฐานข้อมูลจึงเขียนทับคำอธิบายเดิม การเปิดรับจองอีกครั้งก็ใช้เส้นทางเดียวกัน [ปุ่มในหน้าแอดมิน](../../apps/web/src/pages/Equipment.tsx) · [คำสั่งอัปเดตใน API](../../apps/api/src/equipment/routes.ts)

## กติกาที่แก้และวิธีพิสูจน์

แยกค่าเริ่มต้นออกมาใช้เฉพาะตอนสร้างอุปกรณ์ สำหรับการแก้ไข ฟิลด์ที่เว้นไว้หมายถึงเก็บค่าเดิม ส่วนการส่ง `{"description":""}` ยังหมายถึงผู้ดูแลตั้งใจล้างข้อความ [ดู schema หลังแก้](../../packages/contracts/src/index.ts)

เทสต์สร้างอุปกรณ์ที่มีคำอธิบาย ปิดรับจอง แล้วอ่านรายละเอียดผ่าน API อีกครั้งเพื่อตรวจทั้งสถานะและข้อความ จากนั้นเปิดรับจองและตรวจซ้ำ เทสต์ยังยืนยันว่า API ปฏิเสธคำขอแก้ไขที่ว่างเปล่า และยอมให้ล้างคำอธิบายเมื่อระบุฟิลด์นั้นโดยตรง [เทสต์กันบั๊กซ้ำ](../../apps/api/test/api.integration.test.ts#L111) · [ผล CI](https://github.com/KamitomeYuta/LabReserve/actions/runs/42258299080)

## บทบาทและผลบนเดโม

เจ้าของโปรเจกต์เป็นผู้พบอาการ รายงาน และยืนยันให้คืนข้อความตั้งต้นของทั้งสองรายการ AI ช่วยทำให้อาการเกิดซ้ำที่ตัวตรวจข้อมูล แก้ schema เพิ่มเทสต์ และ deploy หลังจากนั้นจึงคืนข้อความเฉพาะรายการที่ช่องยังว่าง การแก้โค้ดป้องกันการสูญเสียครั้งถัดไป ส่วนการคืนข้อมูลใช้ข้อความเดิมที่ทราบและได้รับการยืนยัน [การเปลี่ยนแปลงใน PR #4](https://github.com/KamitomeYuta/LabReserve/pull/4)
